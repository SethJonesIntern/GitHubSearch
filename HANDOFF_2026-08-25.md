## 2. TOP PRIORITY — the 20 "clone failures" are a Windows filename bug

**This is the most important finding of the session and it is not yet fixed.**

All 20 repos in the reclone block failed again. They are **not** deleted from GitHub —
`git ls-remote` confirms 17 of 20 are alive. The real cause:

```
error: unable to create file app/backend/evals/results/generated_results_2025-07-10_16:17:30.jsonl: Invalid argument
fatal: unable to checkout working tree
warning: Clone succeeded, but checkout failed.
```

A filename containing **`:`**, which is illegal on Windows. Git fetches every object
fine, then the checkout aborts, `git clone` exits non-zero, and
`transitive_invokers.shallow_clone` (line 58) returns `False`. The driver records
`{"stage": "clone"}` and skips analysis entirely.

**But the working tree is substantially there.** Reproduced on
`Azure/plan-search-chatbot`: 157 files checked out including **all 36 `.py` files** —
exactly matching `py_files=36` in the audit sheet. Only the one illegal `.jsonl` was
lost. The same is true across the block; the on-disk checkouts survived and several
*grew* (`gabrielmoreira` 13,593 → 13,959 `.py`, `dimagi/commcare-hq` 5,365 → 5,384).

So ~17 repos are sitting fully analyzable on disk and are being thrown away over a data
file we never read. This class also covers `?  * < > | "`, reserved names
(`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`) and trailing dots/spaces — common in
Linux-authored repos. `core.longpaths=true` is already set and does **not** help.

### The fix (not applied — deliberately, see §4)

In `shallow_clone`, treat a non-zero exit as **partial success** when the tree exists
and contains `.py` files, rather than a hard failure:

- catch `CalledProcessError`, check for `Clone succeeded, but checkout failed` in
  stderr (or just test the tree),
- if `dest` exists and has ≥1 `.py`, log a warning, return `True`, and record the repo
  as `clone_partial` so it is auditable,
- keep returning `False` for genuine failures (auth, 404, timeout).

Then re-queue those repos. **Do not** let the driver `shutil.rmtree` them first without
this fix — `batch_call_metadata` deletes the checkout unconditionally before cloning,
so a hard failure after deletion would lose source we currently have. It did not bite
this time only because the clones do partially succeed.

The 3 genuinely gone from GitHub (no checkout, `ls-remote` fails):
`agno-agi/pal`, `holetron/hindsight-mempalace`, `openJiuwen-ai/agent-store`.

### How `imported_by` is computed, and where it leaks

Declared package name (from root `pyproject.toml` / `setup.py` / `setup.cfg`, never a
directory name) → one anchored regex `^[ \t]*(?:from|import)[ \t]+(name)` over every
`.py` in every clone → attribute importers back, dropping names two repos both claim
and names that fail `name_relates_to_repo` (which exists to stop a vLLM fork harvesting
every vLLM importer).

Measured limits:

- **375 of 1,055 repos have no root packaging metadata at all** — the signal can never
  fire for them.
- **297 of 712 declared names (42%) are dropped by `importable()`** — the dominant
  filter by far (`GENERIC_NAMES` and `THIRD_PARTY` drop 5 between them). Of those: 249
  have no matching directory (mostly legitimate — distribution name ≠ import name, but
  it does lose real ones like `NousResearch/hermes-agent` → `hermes_agent`), **12 are
  PEP 420 namespace packages** (a genuine bug — those *are* importable in Python 3:
  `srtab/daiv`, `soliplex`, `Kasma-Inc/Sagi`), and **8 are monorepo layouts nested
  deeper than `src/`** (`chatchat-space/Langchain-Chatchat`, `timbal-ai/timbal`).
- So `imported_by = 0` for ~670 repos carries **no information**.
- **Vendoring inflates the other way**: `hermes-agent` is vendored bodily inside
  `johnson7788/MultiUserClaw` and `aivrar/portable-hermes-agent`. The scan skips
  directories literally named `vendor`/`third_party`, not vendored copies in
  normally-named folders.
- `THIRD_PARTY` contains every `FRAMEWORK_CALLS` key by design, so the top-20
  frameworks' own repos score 0 here. Don't read that as "not a framework".

Fixing the PEP 420 and nested-layout cases (~20 names) requires a full
`audit_framework_check --scan` (~13 min, walks the clone tree) because it changes the
candidate name set.
